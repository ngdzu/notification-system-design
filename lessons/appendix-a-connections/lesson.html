Anatomy of a Connection

Why this appendix exists

Lesson 1 said push works by “the server holding open some channel to the client,” and that this costs resources per connected client, 24/7. This appendix zooms all the way in on that sentence: what a connection is physically, where it lives, how many kilobytes one costs and why, and what actually happens when one dies — say, when you press Ctrl+C in a terminal. Lessons 8, 9, and 10 all get easier once a connection is a concrete thing instead of a magic pipe. This page covers the core idea and the interactive demos; the linked .md files go deeper on each piece.

A connection is memory, not a wire

Between your phone and a server there is no wire reserved for you. The internet is packet-switched: data is chopped into packets — small chunks, each stamped with a destination address — that hop router-to-router, sharing every link with millions of strangers' packets. So where does the “connection” live? In RAM, at the two ends. When a client opens a TCP connection (TCP is the internet's standard reliable transport protocol), both machines run a handshake — a three-message exchange (“can we talk?” / “yes, can you hear me?” / “yes”) — and each side allocates a socket: a kernel data structure (the kernel is the core of the OS) remembering the connection's state, keyed by its 4-tuple (source IP + port, destination IP + port).

↳ Where the socket lives in RAM: kernel-memory-and-sockets.md · how the kernel finds it: socket-table.md · what's inside it (sequence numbers, buffers): sequence-numbers-and-buffers.md

The one exception in the middle: your home router's NAT (the box sharing one public IP among your devices) keeps a small table entry per connection. Remember it — it comes back to bite in the “silence” section.

What one connection costs

Because a connection is memory, its cost is kilobytes, not megabytes: a few KB of kernel socket structure, send/receive buffers, ~10–20 KB of TLS state if encrypted, plus whatever your application keeps per user. A tuned idle connection lands around 10–50 KB — so a million of them is 10–50 GB, and it must be RAM, because kernel socket memory can't swap to disk. The client pays too: keeping a phone's radio awake burns battery, which is why the OS keeps one shared push connection (to APNs/FCM — Lesson 8) rather than one per app.

↳ Full cost breakdown (file descriptors, TLS, buffers): kernel-memory-and-sockets.md and sequence-numbers-and-buffers.md

Threads: the cost that used to be the killer

The obvious server design is thread-per-connection: each connection gets its own thread (an independent line of execution) that sleeps until data arrives. But a thread's default stack is ~1 MB — the design collapses around 10,000 connections, a wall the industry named the C10K problem. The winning answer is event-driven I/O: one thread asks the kernel “which of my 100,000 sockets have data?” via an API like Linux's epoll, then services the ready ones in a loop — the event loop (Nginx, Node.js, Netty). Go's goroutines are a middle path: ~4 KB stacks multiplexed onto a few real threads. Idle isn't free either — both sides send periodic heartbeats to catch silent death and keep NAT mappings alive.

Connections all the way up the stack

“Connection” means something at every protocol layer, and the layers stack. UDP is the connectionless transport — fire-and-forget, no state (DNS, video calls). TCP is the connection described above. TLS layers encryption on it, and HTTP/1.1, HTTP/2, WebSocket, and SSH each reuse, multiplex, or upgrade one TCP connection in a different way. QUIC (HTTP/3) rebuilds TCP's ideas on top of UDP — proving the thesis: a connection is just state plus rules, so you can build one on anything.

↳ Layer-by-layer breakdown: protocol-stack.md

Every layer you add = more per-connection state in RAM at both ends. A WebSocket-over-TLS connection is three agreements stacked: TCP's, TLS's, and WebSocket's.

How connections die — try to kill one

There are exactly three endings, and which one you get depends on a single question: did a goodbye packet make it out? Kill the connection below three ways and watch what the server believes.

FIN and RST are information — the server's belief updates instantly. Silence sends nothing: the server keeps believing, and only a failed write (minutes), TCP keepalive (2 hours by default!), or an app heartbeat (~30 s, shown here at 10× speed) reveals the truth. That stuck state is called a half-open connection.

In short: FIN (“I'm done sending”) is sent by the kernel even when the process is killed by Ctrl+C or kill -9 — the kernel outlives the process and closes politely on its behalf. RST (“no such connection — stop”) is the slam: a crashed peer, a dead port, a load balancer's idle timeout. Silence is the dangerous one — cable yanked, battery dead, kernel panic — no packet at all, so the server's socket sits in ESTABLISHED believing in a ghost until a failed write, a 2-hour TCP keepalive, or a ~30 s app heartbeat reveals the truth.

↳ Full mechanics of FIN/RST/silence, plus the SSH Ctrl+C twist: connection-death-and-detection.md

Back to the notification system

Reread Lesson 1's claim with X-ray vision: “push requires a connection per client” means an event-driven gateway holding ~1M sockets ≈ tens of GB of RAM, ~33k heartbeats/sec of pure overhead, and a ghost window of one heartbeat interval during which it pushes to clients that silently died. That window is why Lesson 10's pull fallback is not optional — and “which of my thousand gateways holds user X's socket?” is exactly Lesson 9's presence problem.

Recap

  • A connection is matching state in RAM at both ends — a shared belief, not a reserved wire. Routers keep nothing (except NAT).
  • One idle connection ≈ 10–50 KB (socket + buffers + TLS + app state); a million ≈ tens of GB of unswappable RAM.
  • Thread-per-connection hits the C10K wall; event loops (epoll — Nginx, Node) and goroutines make millions cheap.
  • The stack layers connections on connections: TCP → TLS → HTTP / WebSocket / SSH; QUIC rebuilds it all on connectionless UDP.
  • Three deaths: FIN (polite — sent even on Ctrl+C or kill -9), RST (slam), silence (half-open — caught only by a failed write, a 2-hour TCP keepalive, or the app's ~30 s heartbeat).
