# Q&A Log — Appendix A: Anatomy of a Connection

## Q1: Is it true that each browser tab opens a unique OS-assigned source port for each connection? It sounds like every connection requires a new port — does the browser open a new port every time we open a URL in a different tab? (2026-07-11)

Yes — this is standard TCP/OS behavior, not a browser-specific trick.

**The mechanism:** when your browser calls `connect()` to start a new TCP connection, the operating system's kernel picks an unused local port from the **ephemeral port range** (temporary, short-lived port numbers — typically 49152–65535, sometimes starting around 32768 on Linux) and binds the outgoing connection to it. The browser doesn't manage this itself; it just asks the OS for a socket, and the OS assigns the port automatically.

**Why this has to happen:** the destination (say, YouTube's server on port 443) is identical for both tabs. The connection's unique identity is the **4-tuple**: `source IP : source port ⇄ destination IP : destination port`. If both tabs used the same source port too, the 4-tuple would be identical for both connections, and the kernel's socket table (a lookup table mapping 4-tuples to socket state) would have no way to tell incoming response packets apart — a packet addressed to `192.168.1.100:54321` would be ambiguous between Tab 1 and Tab 2. Giving each tab a different source port keeps the 4-tuples unique, so each tab gets its own independent socket entry in the kernel's table.

**Generalizing beyond browser tabs:** every TCP connection needs a locally-unique 4-tuple. Since the destination IP/port is often fixed (you're always hitting the same server on port 443), it's the *source port* that has to vary to make simultaneous connections distinguishable. This applies to any app opening multiple simultaneous connections to the same destination — a mobile app polling an API twice, a load-testing tool, `curl` in a loop — not just browsers.

**Important nuance — it's "new connection → new port," not "new request → new port":** HTTP/1.1 and HTTP/2 typically reuse a single TCP connection for multiple requests (keep-alive for HTTP/1.1, multiplexing for HTTP/2) rather than opening a fresh socket per request. So a single tab loading a page with 50 resources from the same origin usually reuses one connection (one port), not 50 separate ones. The "new port" only happens when a genuinely new connection is opened — e.g., a new tab to the same site, or a connection to a different origin.

## Q2: Is a socket created every time there is a connection? When a socket is created, is a port always assigned? Does SSH follow the same principle — create a socket, assign a source port? (2026-07-11)

**Is a socket created every time there is a connection?** Yes, at the TCP layer specifically. A **socket** is a kernel data structure (the kernel is the core of the operating system) that represents one endpoint of a connection and holds its state — the 4-tuple identity, sequence numbers, and send/receive buffers (see the main lesson.md for details). Every time a new TCP connection is established — via the three-message handshake — the kernel allocates a fresh socket on each end to track it. This is true regardless of what's riding on top of that TCP connection: a browser tab, an SSH session, a WebSocket, an HTTP/2 multiplexed set of streams — all of them sit on exactly one TCP connection, and therefore exactly one socket per end, no matter how much application-level activity happens inside it.

The distinction worth holding onto: **"connection" at the TCP layer is 1:1 with sockets, but higher layers can multiplex many logical things onto one TCP connection/socket.** HTTP/2 runs dozens of request streams over a single socket. SSH runs your shell, port forwards, and file transfers as multiplexed "channels" over a single socket. So opening more *application-level* things (more HTTP requests, more SSH channels) doesn't necessarily mean more sockets — but opening more *TCP connections* always does.

**When a socket is created, is a port always assigned?** Yes — a socket's identity is exactly the 4-tuple (source IP, source port, destination IP, destination port), so it cannot exist without a port on each end. For the *client* side initiating an outbound connection, the OS auto-assigns an unused **ephemeral port** (a temporary, short-lived port number, typically in the 49152–65535 range) the moment you call `connect()` — you don't pick it yourself. For the *server* side, the port is usually a well-known, fixed number the server explicitly `bind()`s to and listens on (443 for HTTPS, 22 for SSH, etc.) — that's how clients know where to connect in the first place.

**Does SSH follow the same principle?** Yes, exactly. SSH is "its own encrypted protocol on TCP" (see [protocol-stack](protocol-stack.md)) — meaning an SSH session is just a regular TCP connection underneath, with SSH's own encryption and multiplexing layered on top, the same way HTTPS layers TLS+HTTP on TCP. When you run `ssh user@host`, your machine opens a normal TCP connection: the OS assigns your machine an ephemeral source port (e.g., `54321`), and the destination is the server's IP on port 22 (SSH's well-known port). The kernel creates a socket on each end exactly as it would for a browser connecting to YouTube on port 443 — same mechanism, same rules, just a different destination port and a different application protocol running on top. If you open two simultaneous SSH connections to two different servers (or even the same server twice), each gets its own ephemeral source port and its own socket, for the same "4-tuple must be unique" reason described above.

## Q3: What is a TCP connection, and what are non-TCP connections? Which ones open a socket, and which ones don't? (2026-07-11)

**TCP connection:** TCP (Transmission Control Protocol) is the internet's standard *reliable, connection-oriented* transport protocol. "Connection-oriented" means before any data flows, both sides do a **three-message handshake** ("can we talk?" / "yes, can you hear me?" / "yes") and then each side allocates a **socket** — a kernel data structure that tracks the connection's state: the 4-tuple identity, sequence numbers (which bytes have been sent/acked, so lost or out-of-order packets can be detected and retried), and send/receive buffers. This bookkeeping is what makes TCP *reliable* — it guarantees your bytes arrive, in order, or the connection reports failure. Almost everything discussed in this appendix — HTTPS, SSH, WebSocket — is built on top of a TCP connection.

**Non-TCP connections — the main one is UDP.** UDP (User Datagram Protocol) is described in [protocol-stack](protocol-stack.md) as "the *connectionless* transport: fire-and-forget packets, no handshake, no state, no delivery guarantee." There's no three-way handshake, no sequence numbers, no retries — you just fire a packet (called a **datagram**) at a destination IP:port and hope it arrives. UDP is used where speed matters more than guaranteed delivery: DNS lookups (one query, one reply, not worth a handshake) and video/voice calls (a dropped frame is fine; waiting for a retransmit would cause more lag than just skipping it).

**Which ones open a socket — this is the subtle part.** Both TCP and UDP actually go through the same OS `socket()` system call and both get a kernel socket structure bound to a local port. The difference isn't "socket vs. no socket" — it's *how much state that socket holds*:
- A **TCP socket** holds rich connection state: handshake-negotiated identity, sequence numbers, retransmission timers, buffers — because TCP is tracking an ongoing, ordered, acknowledged conversation.
- A **UDP socket** is much thinner: essentially just "I'm bound to this local port, hand me any datagrams addressed here." There's no handshake to record, no sequence numbers to track, no notion of the datagram having been "acked." It's a mailbox, not a conversation.

So the accurate framing is: **UDP is "connectionless" in the sense of having no handshake and no ordered/acknowledged state — not in the sense of having no socket at all.** Both protocols use sockets as the OS-level plumbing for sending/receiving; TCP's sockets just carry much more baggage.

**One more wrinkle worth knowing (from [protocol-stack](protocol-stack.md)):** QUIC (which powers HTTP/3) runs on top of UDP but rebuilds TCP's ideas — reliable delivery, ordered streams, encryption — at a layer above the raw UDP socket, inside the QUIC library/implementation itself rather than in the kernel. This proves the deeper point the whole appendix makes: "a connection is just state and rules" — you can build TCP-like guarantees on any transport, including one (UDP) that has no such guarantees built in.

## Q4: Then what kind of "connection" doesn't open a socket? (2026-07-11)

Good follow-up — the previous answer was a bit misleading by implying "socket vs. no socket" was the real dividing line. Here's the more precise picture.

**Anything that goes over the network, through the OS's normal networking stack, uses a socket.** That includes TCP, UDP, and even lower-level things like raw IP sockets (used by tools like `ping`, which sends ICMP — a control-message protocol, not TCP or UDP — but still does so through a socket). So within "normal internet networking," there's no connection that skips the socket abstraction entirely — sockets are simply *the* API the OS provides for sending and receiving network data, whether or not the protocol on top adds handshakes and reliability.

So where does a "connection" genuinely *not* open a socket? Two real cases:

**1. Logical/application-level "connections" multiplexed over one real socket.** This is the case that actually matters for you, because the lesson already touches it. An HTTP/2 **stream**, an SSH **channel** (your shell session, a port-forward, a file copy), or a WebSocket message exchange are all things people casually call "a connection" — but they don't each get their own socket. They're independent logical conversations layered on top of a single underlying TCP socket by the *application protocol*, not by the kernel. The kernel only sees one socket with one 4-tuple; SSH or HTTP/2 do their own bookkeeping (stream IDs, channel numbers) to keep the multiplexed conversations apart on top of that one socket. So if someone says "I have 5 SSH connections to this server" meaning 5 terminal tabs multiplexed over one login session, only 1 socket exists — the other 4 are channels, not sockets.

**2. Non-IP "connections" that never enter the TCP/IP networking stack at all.** A USB cable, a Bluetooth pairing, or a serial port connection are all things people call "connections," but they're not part of the IP networking stack (no IP address, no TCP/UDP, no socket() call) — the OS represents them with a different kind of handle entirely (e.g., a device file or a Bluetooth-stack-specific object), because "socket" specifically means the IP-networking endpoint abstraction.

**The takeaway:** within IP networking (which is everything this appendix is about — the internet, HTTP, SSH, WebSocket), sockets are universal — every TCP or UDP endpoint has one. The real fork isn't "socket vs. no socket," it's "one socket carrying one thing" (a plain TCP or UDP connection) vs. "one socket carrying many multiplexed logical things" (HTTP/2 streams, SSH channels) vs. "not IP networking at all" (USB, Bluetooth, serial).

## Q5: Can socket() be called but there's no port or address (yet)? (2026-07-11)

Yes — this is actually the normal sequence, not an edge case. Creating a socket and assigning it a port/address are **two separate steps**, and there's always a brief moment between them (even if it's microseconds and hidden inside a library call) where a socket exists with no address or port attached yet.

Here's the actual sequence, using the real OS system calls as the concrete example (a **system call** is a request an application makes to the kernel — the core of the operating system — to do something privileged, like touching the network):

1. **`socket()`** — this call just asks the kernel "give me a fresh socket object." At this point the kernel allocates the data structure (send/receive buffers, internal bookkeeping) but it has **no IP address, no port, and no destination** yet. It's an unattached, unconfigured endpoint — like getting handed a blank envelope before you've written any address on it. This step returns a **file descriptor** (a small integer handle the application uses to refer to this socket in later calls), but the socket itself is still "empty."

2. **`bind()`** *(optional, mostly for servers)* — attaches a specific local IP and port to the socket. A server calls this to claim a well-known port, e.g. port 443 or 22, so clients know where to find it.

3. **`connect()`** *(for the client side, TCP)* — this is the call that actually fills in the rest of the picture. If the socket wasn't already `bind()`'d to a specific local port, the kernel **auto-assigns an ephemeral port** (a temporary, short-lived port number, typically in the 49152–65535 range) right here, as a side effect of `connect()`. It also records the destination IP and port you're connecting to. Only after `connect()` succeeds does the socket have a complete 4-tuple (source IP, source port, destination IP, destination port) and, for TCP, only now does the three-message handshake happen and the socket become genuinely "connected."

So for the common client case (e.g., a browser opening a tab, discussed earlier in this log), the app typically never calls `bind()` explicitly — it calls `socket()` (empty socket, no port) then `connect()` (kernel silently does the equivalent of an implicit bind, picking an ephemeral port, then completes the handshake). The socket briefly exists in a portless, addressless state between those two calls; it's just that most application code never observes that state directly because `connect()` handles both jobs at once.

For UDP it's similar but looser: you can `socket()` and then immediately start calling `sendto()` (send a datagram to some destination) without ever calling `bind()` — the kernel will auto-assign an ephemeral local port on the first send, since a return address is still needed even for a "connectionless" protocol. So yes: a socket with no port/address is a real, normal, if usually momentary, state — it's the starting point every socket passes through before it becomes useful.

## Q6: Talking about multiplexing — why don't two browser tabs use the same source port and multiplex, the way you said 5 SSH connections can multiplex over one source port? What's the actual difference between those two cases? (2026-07-11)

First, a correction to tighten up an earlier answer: saying "5 SSH connections multiplex over one source port" was imprecise, and the imprecision is exactly what's causing the confusion — so let's fix it, because the fix *is* the answer.

**Multiplexing is not something that happens automatically just because two things are going to the same destination.** It only happens when the client-side application software *deliberately keeps one already-open connection around and reuses it* for a second logical purpose, instead of asking the OS for a brand-new connection. Nothing about "same destination" forces sharing — the OS defaults to giving you a fresh socket (and thus a fresh ephemeral port) every single time you ask for one, unless the application specifically goes out of its way to reuse an existing one.

**The SSH case, corrected:** SSH channels (your shell, a port-forward, a file copy) multiplex over one socket only when they're all part of **the same running `ssh` client process/connection** — e.g., you opened one `ssh` session and, within it, also asked for a port-forward. The SSH *protocol* has a built-in "channel" primitive for exactly this, so anything sharing one `ssh` process gets multiplexed automatically, no configuration needed.

But if you open **5 separate terminal tabs and type `ssh myserver` in each one**, that's 5 independent `ssh` client processes with no shared state between them. By default, each one opens its own brand-new TCP connection — 5 sockets, 5 different ephemeral source ports — exactly like the 5 browser tabs. They do *not* multiplex by default. The only way to get 5 terminal tabs to share one TCP connection is to explicitly configure OpenSSH's **`ControlMaster`** feature: the first `ssh` invocation becomes a "master" connection and leaves behind a Unix domain socket (a local, filesystem-based socket used for inter-process communication on the same machine, not over the network) as a control file; subsequent `ssh` invocations to the same host detect that control file and, instead of opening a new TCP connection, ask the master process to open a new *channel* on its existing connection. This is opt-in — most people never configure it, so most people's "5 SSH tabs" really are 5 separate sockets.

**So the honest comparison:**
- **Two browser tabs, by default:** two independent navigation actions, each triggering the browser's network stack to ask the OS for a connection. If no already-open, idle, reusable connection exists, the OS hands back a fresh socket with a fresh ephemeral port — hence two different ports, as the main [lesson.md](lesson.md) describes.
- **5 `ssh` tabs, by default:** exactly the same story — 5 independent processes, no shared state, 5 fresh sockets, 5 different ports. My earlier framing suggesting this "multiplexes" was wrong unless `ControlMaster` is configured.
- **What genuinely differs between the two:** SSH *can* be configured to detect "hey, there's already a connection to this host open, let me piggyback on it" (via `ControlMaster`), because OpenSSH ships that feature. A vanilla browser tab doesn't have an equivalent explicit user-facing toggle for tab-to-tab sharing, though (as a related, separate point) modern browsers *do* automatically reuse or "coalesce" one already-open HTTP/2 connection across multiple tabs hitting the *same origin*, purely as a performance optimization inside the browser's own connection pool — this happens silently, without any user configuration, whenever the browser's network stack finds a compatible open connection to reuse instead of opening a new one.

**The general rule underneath both cases:** whether something new "multiplexes" onto an existing connection or gets a fresh socket/port depends entirely on whether the software actually asks "is there already a usable connection I can piggyback on?" before opening a new one — and whether it's designed/configured to do that at all. TCP and the OS never force sharing; at best they make it possible when the application chooses to look for and reuse an existing connection.

**Gap flagged in the lesson:** the main `lesson.md`'s Tab 1/Tab 2/Tab 3 example (and the diagram of 3 different source ports) is accurate for the common case — but it doesn't mention that browsers can and do share one TCP connection across tabs to the same origin (HTTP/2 connection coalescing). It's a reasonable simplification for teaching the 4-tuple/ephemeral-port concept, but worth knowing it's not an absolute rule.
